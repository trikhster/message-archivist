# Decisions

Why things are the way they are. Newest last. Add an entry when you make a choice someone might later want to undo, with what was rejected and why.

### No build step, no dependencies
Plain JavaScript files loaded as they are. Anyone can read what runs, `Load unpacked` works straight from the repo, and there's no supply chain to audit. Cost: no modules or types; big files (see [[Known issues]]).

### One library folder (0.4.0.0)
Every backup (one chat, a list, schedules, everything) goes into one folder with one index and one viewer, instead of a zip per run. Chats saved at different times stay together and only changed chats are rewritten. Only date-range copies are still zips. This was a major version: older exports are brought in with Settings → Import.

### The writer frame owns the folder
Content scripts can't use the extension's stored folder handle (see [[Gotchas]]). An extension iframe on the page can, and blobs pass to it without copying. Rejected: sending every file through the background worker (JSON-only messages, base64 overhead).

### Completeness is shown with evidence
"Reached the first message" is only claimed with evidence (a short batch, then quiet tries with no spinner), and every chat gets checks in `progress.json`. A backup that's merely probably complete says so. People use this for records, sometimes legal ones.

### Never log message text
Logs carry names, numbers, times and file names, so people can share them for help, but never message text. Diagnostics mask text too.

### Deleting moves, never deletes
Deleting a chat or duplicate photos moves them into `removed-chats/` or `removed-duplicates/`. Nothing in the backup is destroyed by the extension.

### Labels and flags are notes, not record (0.4.2.0, 0.4.5.0)
They live in `labels.json` / `labels.js` and are left out of `SHA256SUMS.txt`: the checksums vouch for what was read from Messages, not for later annotations. From 0.4.5.0 flags are saved there too (before, only in the viewer's browser).

### Save as it goes: journal plus compaction (0.4.5.0)
Rewriting a big `messages.json` every few seconds is slow, and saving only at the end lost work and held whole chats in memory. Small journal pieces every 15 s / 100 messages, folded in every 3 minutes, make a crash lose almost nothing. Pieces aren't checksummed because they're temporary.

### A photo master list, derived from the record (0.4.5.0)
`messages.json` stays the source of truth; `media-index.json` / `.csv` and the counts in `data.js` are rebuilt from it on every save. The status is computed (`mediaStatus`), not stored, so it can't disagree with the files recorded. This is what lets speed runs, fetch-later and upgrade-later go straight to the photos that need work.

### Full-size photos between batches by default (0.4.5.0)
Opening photos in Messages' viewer while it fetches the next batch uses time that was otherwise idle. It was an opt-in experiment from 0.4.1.0 to 0.4.4.2 and behaved well, so it's on by default.

### Developer notes in an Obsidian vault (`notes/`)
Kept at the repository root, outside `extension/`, because everything in that folder is loaded by Chrome and zipped into releases.

### One settings definition, basic and advanced (0.5.0.0)
Settings had grown three "full size" switches, two window switches and popup-only choices, each with its own defaults in five files. 0.5.0.0 has one shared definition (`GMLib.normalizeSettings`) and one setting per decision, split into a Basic list (what most people ever change) and an Advanced list. Old choices are migrated only where they were clearly made on purpose; otherwise the new defaults apply.

### Defaults aim at "put it back on a phone" (0.5.0.0)
The end goal for most people is a backup they can restore to an Android phone with SMS Backup & Restore. So photos are on and full size, contact cards (numbers) are always captured, and the restore file includes photos. Full size costs little extra because most viewer work happens while Google Messages fetches the next batch.

### One list of chats in Settings (0.5.0.0)
"Chats kept up to date" and "Check for problems" showed the same chats twice with different information and buttons. Now every chat is one row with its status, photos and automatic schedule; filters replace the separate tables.

### Draw a month at a time, not virtualised rows (0.5.0.0)
Months are the viewer's natural unit (the scrubber, jump to month, the headings), they're small enough to draw at once and big enough to keep IntersectionObserver traffic low. Full row virtualisation would have meant fixed row heights, which messages with photos and quotes don't have.

### Don't connect to the phone directly (0.5.0.0 research)
ADB can't read the SMS database without `READ_SMS`; an app that can already exists (SMS Backup & Restore). Importing its XML is the faster path. See [[Android direct connection]].

### Our own Android app for restores (0.5.0.0)
Instead of handing users to SMS Backup & Restore, the project has its own Android app (`android/`), and its own [[Restore package]] format: a tar of JSON lines and plain photo files, written a piece at a time, so years of photos never pass through base64 or memory. Kotlin, with no libraries for the restore itself. The XML for SMS Backup & Restore stays available as a fallback. Restore first; reading the phone's own messages comes next.

### Compose and Material 3 for the app's screens (0.5.0.0)
The first version of the Android app was built from plain Android views to keep it library-free. Its screens are now Jetpack Compose with Material 3 (the Compose BOM, `activity-compose`): it's what Google's own apps are built with, so the app looks and behaves like them (the phone's own colours on Android 12+, dark mode, animations) for little code. The restore itself still uses only the platform. Cost: a bigger app (about 10 MB as a debug build); a release build shrunk with R8 would be much smaller.

### Phone backups in the same format, with READ_SMS only (0.5.0.0)
The Android app backs a phone up into the [[Restore package]] format rather than a format of its own: one reader, so a phone backup restores on any phone, and the extension can learn to import it once. It reads with the `READ_SMS` permission instead of becoming the SMS app: nothing about the phone changes, and there's no switching back. The extension brings a phone backup into its library as one more import source, matched by phone number (below).

### Phone backups join the library by number, with looser message matching (0.5.0.0)
A phone has no Google conversation or message IDs, and names chats from its own contacts, so a phone chat is matched to a library chat by its set of phone numbers (`phoneKey`: last ten digits), falling back to the name only for a library chat with no numbers. Messages can't use `keyOf` either: Google Messages for Web sometimes shows a photo and its caption as two messages, and its minute can differ from the phone's by one. So a phone message is "already there" if the library has one from the same side within a minute either way with the same text (or a photo, for a photo-only message), each library message vouching for one phone message. The risk is the other way round (two genuinely different messages taken as one) only for identical texts from the same side within two minutes, which the one-to-one vouching mostly covers.

### Phone first, then the extension (0.5.0.0)
A phone backup takes minutes where Google Messages for Web takes hours for years of texts, so new users start there: the app's first screen leads with **Back up this phone**, its done screen points to the extension, and the extension's first-run steps put "Start with your phone" right after choosing a folder. The extension then fills in what the phone lacks and keeps the backup up to date. For that to be safe, a backup from the web **claims** messages that came from the phone (`GMLib.phoneClaims`) instead of saving them again: the same loose rule as importing, used the other way round, and once claimed a message has a Google ID and is matched normally.

### Phone backups are updated, not made again (0.5.0.0)
An update appends to the backup file (tar entries after the old ones; the last copy of a name wins), and a chat that only gained newer messages gets one more small piece (format version 2, `files`) instead of being written again, so a daily backup of years of texts reads and writes only the day's messages. Writing a chat again in full is kept for when its older part changed (a restore added messages, or photos are wanted now), at the cost of an unused old copy in the file. Alternatives: a new file per day (simple, but restoring or importing needs all of them, and online storage can't create files in a folder from the background), or rewriting the file every day (gigabytes a day with photos). A file on Google Drive can't be written in place, so it's still updated through a copy; that's the cost of keeping the app without internet access or a Google sign-in.

### The daily backup is a JobScheduler job (0.5.0.0)
No WorkManager (another library) for one periodic job: `JobScheduler` does it with the platform. An update takes seconds, well within a job's time; a job Android stops leaves a whole file and carries on next time.

### Reactions sent as texts are shown, not rewritten (0.5.0.0)
A phone stores a reaction that couldn't travel as one as a text (`❤️ to “…”`). The viewer shows it on the message it quotes; the backup keeps the text as it came, so the record isn't changed by a guess about which message it meant.

### One order and one number format for every list (0.5.0.0)
Favourites first (pinned in Google Messages, a starred contact on the phone, or the Favorites label), then chats with names A–Z, then those known only by a number, shown as "(555) 020-0001" (North America) or "+44 …": in the viewer's dropdowns and chat list, and Settings' lists. Stored titles aren't changed; only what's shown.

### "From phone" instead of "Unfinished" (0.5.0.0)
A chat from a phone backup has every message the phone had, which is usually the whole chat; calling it Unfinished sent people to fix something that wasn't broken. It gets its own status, counted as backed up; a backup from Google Messages later checks it to the first message as for any chat. Imports of older exports take the export's own record of how far it got.

### A new application, Message Archivist, from one first commit (0.0.1.0)
Going public, the project took one name, **Message Archivist**, for the extension and the app alike, and a new repo, `trikhster/message-archivist`: the earlier name tied it to one service and to "scraping", while it now backs up and restores phones and may read more than Google Messages later. It starts as a new application: version 0.0.1.0, a new Android package (`io.github.trikhster.messagearchivist`) and a repository whose history begins with one commit of the code as it stood. The development before that stays private; its commits carried a personal email, and GitHub keeps every pull request's original commits even after a history rewrite, so a fresh repository was the only way to leave none of it public. Formats didn't change: libraries and backup files made before still open (the viewer still reads flag files made under the old name).

### Releases are pre-releases while the version starts with 0 (0.0.1.0)
The first part of the version is the production level (see [[Releasing]]); until it's 1, GitHub marks every release as a pre-release. GitHub's "latest release" link and shields.io's default badge skip pre-releases, so the README links to the Releases page and the badge includes pre-releases.

### The APK is signed in GitHub Actions from repository secrets (0.0.1.0)
A release's APK must always be signed with the same key, or updates won't install. The key was made on the owner's Mac (password in the Keychain) and given to the Release workflow as two secrets; it's on the runner's disk only for the build step. Tag-push workflows only run for people who can push tags, and pull requests from forks never see secrets. The actions in that workflow are pinned to commits so a moved tag can't change what runs next to the key.


### One archive for every app, by importing each app's own export (unreleased)
The library holds every conversation, whichever app it was in ([[Sources]]). Other apps come in from **the export each app already offers** (WhatsApp's "Export chat", Telegram Desktop's JSON, Discord's data package, Meta's and TikTok's "Download your data", Messenger's download of its encrypted chats, Snapchat's "My Data"), read entirely on the computer: no logins, no scraping of their websites, nothing sent anywhere, and no dependence on pages that change. Each chat keeps its app (`service`) and its own folder, and joins only chats of the same app: the same person's texts and WhatsApp chat are two conversations, linked in the viewer, not merged, because each app's record should stay as that app had it. Google Messages' texts (the `sms` service, labelled "Google Messages") stay the default and keep their folders, so every existing library is already a valid archive.

### Snapchat: chats, not snaps; WhatsApp and Messenger: their exports, not their databases (unreleased)
Snapchat's "My Data" lists every snap sent and received (`snap_history.json`) but keeps nothing of them: who, when, photo or video. Brought in, they'd bury the chats under entries with nothing to see (a daily streak is hundreds), so only `chat_history.json` comes in, marked partial because Snapchat deletes what wasn't saved. WhatsApp has no whole-account export with messages, and Messenger's encrypted chats aren't in Meta's main download; the phone's or computer's own databases would have everything, but they're encrypted (Android) or need a native helper (a Mac, an iPhone backup), so those wait for the helper ([[Desktop app]]) and the exports each app offers come first. An export the importers can't read but recognise (an HTML download, one part of several) gets advice, not just "can't read this".

### Snapchat for Web: read what the owner reads, never act (unreleased)
Snapchat's download has only saved messages, so the rest are read from Snapchat for Web, as the owner reads them. Snapchat tells people about screenshots and saves, opening a chat sends read receipts and starts unsaved messages' deletion, and it locks accounts it catches using third-party tools. So the reader is **passive and read-only**: it reads the HTML of chats the owner opens (not screenshots: the owner asked that nothing be treated as a snapshot), never clicks, types, scrolls or changes the page (no panel in it, unlike the Messages page), never opens a Snap or reads one (Snaps aren't chat messages), and sends what it reads to the extension, which keeps it until the owner puts it in the archive. Not by intercepting Snapchat's own traffic (exact IDs and times, but code injected into the page's world and its worker, and Snapchat's protocol to decode), and not by opening chats itself (read receipts and deletions the owner didn't cause). The cost: a chat is kept only once opened there, a group's later messages carry the group's time and span rather than their own, and photos are noted, not saved. Off unless turned on, with its own optional permission for snapchat.com.

### Every app a module beside Google Messages, on the computer and the phone (unreleased)
The archive grew from Google Messages alone to many apps, and each app's facts were spread over five places (the library's list of services, the viewer's own copy of it, the pages' script tags, Settings' text, the importer file). Now each app is **one module file** (`extension/modules/<app>.js`): its name, colour, folder, what identifies a person there, how to get its export, what the phone does with it, and its reader; Google Messages is the core, in `library.js` itself, because the extension and the Android app back it up themselves. Everything else reads the modules (`GMLib.addModule`, [[Importers]]), and Settings' **Apps** tab is built from them. Modules are loaded wherever the archive is read or written, the Messages page's content script included, because folders, labels in the Obsidian notes and People need them there too; the cost is three script lists to keep (Settings, the viewer, the manifest), which `npm run check` keeps honest. The Android app gets a section per app beside Google Messages's (the plan in "One section per app" below): a phone can't read another app's chats, but it's where WhatsApp's "Export chat" and the other apps' downloads land, so they're **shared to the app and kept in the phone backup**, byte for byte, for the extension to read with the same modules. Copied into the app's storage, because a share's permission ends with it, and dropped from there once a backup file has them. Not the other way round (the phone reading them): one reader per app, in one place.

### A small updates file instead of re-uploading a backup online (unreleased)
Google Drive can't add to a file, and the app can't create files in a Drive folder by itself (Drive doesn't offer folder access to apps), so a backup kept there was rewritten and uploaded whole every run. The fix keeps the format: the user makes one more file beside it once, and each run rewrites that small file with everything since the big file's last catch-up, as an ordinary package (so restoring and importing need nothing new, just the two files in order). The big file catches up when the updates uploaded since equal its size: rewriting it then costs no more than what's been uploaded, the classic point to switch. A file on the phone doesn't need any of this: it's added to in place.

### A copy on the phone of a backup kept online (unreleased)
A run used to download the whole Drive file to the cache, add to it, upload it and delete the download; reading the Drive file back was also how it learnt the file's state, and a Drive upload still pending reads back as an empty file ([[Gotchas]]), which made the app write the whole backup again. Now the app keeps that copy (`PhoneCopy`, in `noBackupFilesDir`), adds to it in place and only ever uploads: the phone copy is the working copy and Drive the one people see. The space isn't new (each run already needed room for the download), it just stays. It's on by default for a file online, one switch in Settings (clearing it without turning it off would only make the next run download it all again, so there's no separate "clear"), and it's dropped when free space falls under a tenth of the phone's storage (at least 1 GB). It's started from the Drive file, once, not rebuilt from the phone, because the backup keeps messages already deleted from the phone. Alternatives: a visible file in Downloads (a file picker, a permission, and the user could move or delete it), or making the phone file the automatic backup and copying it to Drive (the app can't create files in a Drive folder by itself). The cost: changes made to the file on Drive by anything else are overwritten by the next run.

### Smaller phone backups: gzipped chats, one copy of each photo, compacting (unreleased)
A backup's text is most of a backup without photos and compresses 10–14×, so each chat's file is gzipped (format 3: by the file's name, so old files read as before and an update can mix them). The whole package isn't compressed (a `.tar.gz`): an update adds to the end of the file and readers seek straight to an entry, and both need an uncompressed tar. Photos are kept byte for byte (already compressed; shrinking them would lose quality), but a picture that arrives twice is stored once, found by size then SHA-256, so nothing is ever matched by a guess. Each run's manifest is left behind by the next, so the manifest is written compact, its history capped, and files the app owns are compacted by writing a new file and renaming it over the old one, never in place: a phone switched off halfway must leave a working backup. The cost: older app and extension versions can't read version 3 (they say to update first).

### One section per app on the Android app's screens (unreleased)
The app may later handle other apps, so its first screen and Settings are organised by app: a **Google Messages** section (this phone's texts, picture messages and RCS chats) holding the status card, the one-off backup and restore, and in Settings its automatic backup. Another app gets a section like it rather than more buttons in one list. The status card has a single main button (Back up now, or the first backup, whose done screen offers automatic backup), so the home has one obvious thing to do.

### Two levels: source, then account (unreleased)
Texts come from more than one place: Google Messages, iMessage (with an iPhone's SMS), and more than one number (a second phone, a work number). Calling them all "Text messages" would mix them up, and matching chats by the other person's number alone would merge a second number's chats into the first's. So a chat has a **source** (the app its record came from) and an **account** (which of your numbers or IDs in it), and joins only chats with both the same ([[Sources]]). Existing chats are each source's main account, with nothing to migrate. The phone backup says its own number when it can; when nothing says, the main account is assumed, and the one ambiguous case (chats here, no number on record, a backup naming one) is asked once.

### People: numbers join by themselves, names are only suggested (unreleased)
The owner wants one person across apps, accounts and numbers. What can identify someone differs by app: a number (texts, WhatsApp, iMessage), an email, an app's own user ID or username (Telegram, Discord, TikTok, Snapchat), or only a display name (Instagram, Messenger, and WhatsApp for saved contacts). Numbers, emails and handles are reliable, so chats that share one are one person without asking. Names aren't (two "Sam"s; an Instagram name chosen by its owner), so a name in common is a suggestion the owner accepts or turns down, with "join all" for a long list. Earlier, the viewer linked chats by name too, silently; that's now a dashed "maybe" chip. The owner's decisions are kept per **chat** (`people.json`: joined, apart, alone, names), not as a list of people, so people are worked out afresh from the archive each time and a new chat with a known number joins its person by itself. They're the owner's notes, like labels: saved by the viewer, not in the checksums. See [[Sources]] → People.

### Obsidian notes inside the backup folder, opened as the vault (unreleased)
Notes for Obsidian need the photos, and Obsidian can only show what's inside its vault, so the vault is the backup folder itself and the notes go in its `Obsidian/` folder, embedding photos from the chats' own `media/` folders: nothing is copied, and the archive stays one folder. A separate vault elsewhere would have meant copying every photo. The notes are derived (rewritten when the archive changes, never the record) and open to the owner's writing (anything below a "Your notes" line stays), so they're kept out of `SHA256SUMS.txt`. Messages go a **year to a note, a month in a busy year, and a short chat in its own note**: a note per month for every chat made over 100,000 notes from a made-up archive of 1,500 chats, most of them one or two messages; the adaptive split made 3,400. See [[Obsidian notes]].

### The whole address book, opt-in, to tie every app's chats to contacts (unreleased)
To map every message to a person across apps, the archive needs what the phone's contacts know about people who aren't in its texts: a WhatsApp export names saved contacts but gives no number, and a Telegram chat may come from someone's other number. So the Android app can save every contact (*Save all my contacts*), in its own entry of the backup, and the archive keeps the newest as `contacts.json`. It's **off at first**: it puts everyone's details (numbers, emails, work, birthdays, relations) into a file that may sit on Google Drive, most of them people never messaged. Never postal addresses or contact notes. A **name ties a chat to a contact only in apps whose names come from the phone's contacts** (texts, WhatsApp, Signal, iMessage) and only when one contact has it; elsewhere names are what people call themselves, so they stay suggestions. The address book never makes people by itself: People and the notes stay those you have chats with.

### Obsidian: days, events, photos and phrases, found by rules (unreleased)
The notes also read the conversations for what happened and when: a **calendar** (a note a year and a month, each day linking to it in each chat), **events** found by phrases (birthday and anniversary wishes, congratulations and a guess at what for, holiday greetings, travel, meeting up, photo days), every **photo** by day, **phrases** as topics, and a **timeline** per person. All by rules and counting in the extension, like the rest: repeatable, private and cheap, at the price of being English-leaning and sometimes wrong, so events are written as likely ("Probably met up", "engagement?", *probably* 4 May) and every one links to its day so it can be checked. **Nothing about illness, grief or loss is looked for**: a wrong guess there would hurt, and a right one isn't the archive's to label. Birthdays come from the contacts first; otherwise from the days someone was wished happy birthday, *probably* only when the same day comes up in two years. A month note lists every day rather than having a note a day, which would make thousands of tiny notes. Years and months end with the "Your notes" line, so the calendar can double as a journal. One-way senders stay out of all of it, or codes and alerts would fill every day. Phrases are kept only when they stand out against everyone else's, and of a phrase and its variants the one more people share stays, since shared phrases are what link people.

### Obsidian: the person at the centre, worked out without a model (unreleased)
People's notes are hubs: the gist, moments, years, when you talk, connections, photos and links, so the graph is people joined by topics, mentions and groups rather than a pile of chat notes. All of it is counting (TF-IDF for topics, capitalised first names for mentions, pauses of six hours for conversations), done in the extension with no model and nothing sent anywhere, and repeatable: the same archive makes the same notes. What each one-to-one chat says is kept in the manifest (`a`) so an unchanged chat still isn't read; that costs a few MB of manifest on a big archive. Topics become notes only when **two people or more** share them (one person's words stay plain text on their note), so topic notes connect people instead of multiplying. Group chats aren't analysed: who said what in a group would need each sender matched to a person.

### An app on Chrome or Edge rather than Tauri or Electron (proposal)
The owner wants to launch the archive like an app but keep Chrome or Edge as its engine. An installed web app does exactly that and reuses every page and module as they are, with no second engine (Tauri's WebKit lacks the File System Access API the pages use) and no 100 MB download (Electron). What no browser can do (iMessage's `chat.db`) goes to a small native helper reached by native messaging. Not built; the decisions it needs are in [[Desktop app]].

### The app is the extension's own pages, with stand-ins, served from release tags (unreleased)
The installable app ([[App]]) reuses Settings and the viewer as they are: `app/app.js` stands in for the handful of extension APIs they call, and `html.app` hides what needs Google Messages. A second UI would have drifted from the extension's. At first Settings was the home page and the viewer opened in a second window; the owner found the archive hard to find ("I can't see the archive in the app, only the settings"), and then asked for viewing to be part of the Settings page itself. So the viewer is Settings' first tab, **Archive**, in a same-origin frame (`viewer.html?library=1&embedded=1`), and Settings opens on it once there's a folder, in the extension too ("Open my backup" opens `options.html#archive`). A frame rather than merging the two pages: each is ~2,000 lines with its own ids, `$` and keyboard shortcuts, and the viewer must also run alone (the copy in the backup folder, the Messages tab's analyzer).
- **Served only from release tags** (`pages.yml`), with every file's SHA-256 in the release: a web app runs whatever its address serves next, so what's served is exactly a tagged, checked and tested release, and anyone can compare it. A strict content security policy keeps the pages from loading or sending anything anywhere else.
- **The backup folder gets the extension's viewer, unchanged** (`archive/viewer.html`): the app's copy carries the policy and `app.js`, which would stop `index.html` opened from disk loading its own scripts.
- **A new version waits** until every window of the app is closed (or **Restart now**): never a page swapped under someone in the middle of an import.
- **Not shared with the extension:** settings, past runs and folder access belong to each origin. The app asks for the folder once, and its Obsidian switch is its own. The app starting the extension's backups (`externally_connectable`) is the next phase ([[Desktop app]]).

### Codes and spam: told apart per chat, kept apart in the viewer, left out only when asked (unreleased)
An archive seeded from a phone is full of one-time codes, promotions and automated texts. They're judged **per chat**, by who sent them (a short code, a sender ID, a number with no name) and what came in (codes, the words marketing texts must carry, scam-like links): one message can't say what a chat is, and a chat is what's kept or not. Anything that looks like a conversation (three messages of yours, any reply to a contact), a group, or a chat the owner labelled is never one, because a wrong guess here hides or leaves out something that mattered. The viewer only **keeps them apart** (folders of their own, one click to show them everywhere, "It's not" to correct a guess); **leaving them out of the archive** is off until the owner ticks it, and even then what's already there is only moved to `removed-chats/` after they've seen the list. A chat left out for a reason comes back if that switch is turned off. Kept on the chat rows (`traits`) so "Back up everything" can skip what's already in the archive without opening it. See [[Sources]] → Kept apart.

### The same leave-out rules on the phone, in Kotlin, held to shared cases (unreleased)
Phone backups leave out codes, promotions and automated texts by the extension's rules, written again in Kotlin (`Clutter.kt`): the app can't run the extension's JavaScript, and a second set of rules would drift. Both are tested on one file of cases (`test/filters/cases.json`): the extension's `npm test` and the app's `testDebugUnitTest` in CI. A backup that had such a chat drops it from its manifest rather than rewriting the file: the phone still has the texts, and the dropped pieces go when the file is compacted, like any superseded chat. A starred contact plays the part labels play in the archive: never left out.

Marketing texts word their opt-out line every which way ("STOP=end", "Stop2End", "Rply STOP", "End=STOP"), so those lines match in any capitals. "End", "quit" and "cancel" after *reply* or *text* match only in capitals, since in lowercase they're everyday words ("I'll text end of day"). Sales words (sale, % off, shop now, promo code) count only beside a link from a number with no name, like the scam words, so a friend mentioning a sale isn't a promotion. The rules carry a version (`TRAITS_VERSION`) because the archive's index keeps each chat's counts: a chat counted by older rules is counted again where those counts are used, rather than every chat being read again at every backup.

### Backing up some chats: chosen each time, never a setting (unreleased)
Backing up only some chats is for a one-off file (a conversation to keep or share), so it's chosen on **Back up this phone** each time and never saved: automatic backups are always of every chat, and a run of some chats doesn't count as the automatic backup's run. Choosing is explicit, so a chosen chat goes in even when Settings would leave it out; the list starts as an ordinary backup would (those kinds' chips off), and left that way it *is* an ordinary backup, so opening the list changes nothing. Its type chips decide what's in the backup, not only what's listed: a chat of a hidden type is never backed up, ticked or not, so nothing out of sight goes in. Sizes are worked out only while the list is open, in the background, since they mean asking the phone for every photo's size. An update of some chats never drops the file's others: it brings the chosen ones up to date and carries the rest over as they were.
