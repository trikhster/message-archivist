# Android app (`android/`)

Backs a phone's texts up into a [[Restore package]] file and keeps that file up to date (by hand or by itself, every hour to every 30 days), and puts such a file back on a phone. Its launcher name is Message Archivist, like the extension's, and its package is `io.github.trikhster.messagearchivist` (since 0.0.1.0; test builds from before used another package, so they don't update to it). The launcher icon is the extension's speech bubble, white with blue dots on Google blue, with a backup-and-restore badge (Material "history"); themed icons and notifications use the bubble alone. Kotlin, minSdk 26 (Android 8), target 35. The screens are Jetpack Compose with Material 3, so it looks like Google's own apps: the phone's own (wallpaper) colours on Android 12+, Google blue before, light and dark (see [[Decisions]]). Nothing else beyond the platform: JSON is `org.json`, the tar reader is ~60 lines. No internet permission: it never sends anything anywhere.

## The one rule that shapes it
Android only lets the **default SMS app** write to the SMS/MMS database. So the app becomes the default SMS app for the restore (the system asks the user), then the user makes Google Messages the default again. To be allowed the role an app must have the parts of an SMS app; `DefaultSmsParts.kt` has the minimum:
- `SmsReceiver`: a text arriving during the restore is saved to the inbox and a notification says so.
- `MmsReceiver`: a picture message arriving during the restore can't be downloaded here; a notification explains Google Messages fetches it afterwards.
- `ComposeActivity`: "send a text" requests from other apps get a short "use Google Messages" screen.
- `HeadlessSmsSendService`: quick replies to calls are ignored.

Check the role with `RoleManager.isRoleHeld(ROLE_SMS)` (`RestoreService.isDefaultSmsApp`), **not** `Telephony.Sms.getDefaultSmsPackage()`: that returns null to a non-system SMS app asking about itself (it also requires a cell-broadcast app-op only system apps can get). Found the hard way; see [[Gotchas]].

## Screens (`Screens.kt`)
One activity; `RestoreApp` picks the screen from the state and cross-fades between them. Back from a review or a result goes to Welcome; Settings and the two reviews have a back arrow and their own title in the top bar. The first screen and Settings have **one section per app** (`SourceHeader` on the home, `SectionTitle` in Settings): **Google Messages** (this phone's texts) first, then on the home a section for each other app (`AppSection`, `Apps.all`) ([[Decisions]]).
- **Welcome** (the home): a settings gear in the top bar, then the **Google Messages** section. First a **status card**: backed up (when, and to which file), automatic backup on but not run yet, the last run failed (why), or not backed up yet; this phone's messages, chats and photos (`PhoneBackup.summary`, counted on resume when it may read texts); one button, **Back up now** (automatic backup on) or **Back up this phone** (the review below; its done screen offers automatic backup), and **Settings** only after a failed run. Then a list (`ActionRow`): **Back up to another file** (once automatic backup is on) and **Restore a backup** (the file picker; a file that can't be read shows its error under it). If the SMS permission was refused, a card with **App settings**.
- **Other apps** (on Welcome, after Google Messages's section): for each app its colour and two letters (as the archive shows it, no app's logo), how many of its exports are waiting for the next backup or in one, a card with how to get its export here (a share from WhatsApp; a download for the others, shared or added), its last five exports (title, size and "waiting for your next backup" with **Remove**, or "In <file>"), and **Add a file…** (`OpenMultipleDocuments`, taken as that app's when the files don't say). A note under them says these go into the next backup and into the archive with it. **Sharing to the app** (`ACTION_SEND` / `ACTION_SEND_MULTIPLE` of a .zip, .txt, .json or any file, not images): `MainActivity.shared` takes the streams (or the clip), `addExports` copies them in the background ("Adding it to your phone backup…") and the home shows **Added to your phone backup** (with **Back up now**) or why not (not an export from those apps; text rather than a file). The intent's action is cleared once handled, so turning the phone doesn't add it twice.
- **Settings** (gear; back arrow or Back returns): *Google Messages*: **Back up by itself** (turning it on asks for a **New file…**, backed up now, or **A backup I already have…**, brought up to date now); the last backup (or why it failed) and **Back up now**; the file (on this phone or online) with **Change** (the same two choices, under it); **How often** (filter chips: hour, 6 hours, 12 hours, day, week, and **Custom…**, a dialog for any number of hours or days within `Daily.HOURS` = 1–720; a note that Android may wait longer, and a warning when the file is online, without an updates file, and it's under 12 hours); **Include photos and videos**; **Only while charging**; **Only on Wi-Fi** (on by default for a file online); **Tell me after each backup**. *Backup online* (a file online only): **Keep a copy on this phone** (its size, "made at the next backup", or left out for space) and the updates file. *About*: version, "no internet access", and **App permissions** (Android's page for the app). Each change reschedules the job (`Daily.enable`).
- **Review**: the backup's date, an estimate for the ticked chats, messages / chats / photos (with their size); why the app becomes the SMS app; every chat with a tick (all ticked; **Select all** shows a dash when only some are), newest first, with avatar, message count, years and "Group". The bottom bar has **Choose another file** and **Restore N messages**. Only some chats ticked: their files go to the service as `EXTRA_THREADS`. Groups and no known own number: a number field appears.
- **Running**: a ring with the percentage and "n of total", the chat being restored, time left, texts / picture & group / already here, **Stop**. The screen stays on. The notification shows the same with a Stop action.
- **Done**: finished, "already on this phone" (same file again), stopped, or failed. While this is still the SMS app: a **One more step** card with **Switch back to Google Messages** (opens it; it asks to be the SMS app again) and **Choose SMS app in Settings**. Afterwards: **You're all set**. Then **Restore another file** (to Welcome), or after a stop or failure **Restore again** / **Try again** (back to the same file's review).
- **Backup review**: this phone's messages, chats and photos (`PhoneBackup.summary`), **Include photos and videos** (on), **Chats** (*All chats*, or *N chats chosen* with **Back up all chats instead**; it opens Choose chats; with chats chosen, the line under the title and the update card say so, and the leave-out line isn't shown), what's in a backup (and the RCS caveat below), **Update a backup instead…** (`OpenDocument`: a backup made before); **Back** / **Save backup**, which opens Android's save screen (`CreateDocument`, `messages-backup-<date>.tar`). Either way the file's permission is kept (read and write, `takePersistableUriPermission`) for the daily backup.
- **Choose chats** (`ChooseChats`, `ChooseBar`, `SortMenu`): the phone's chats, read the first time it opens (`PhoneBackup.chatList`: newest first, named from contacts, each with what `kindOf` makes of it, `ChatInfo.kind`), then each one's size in the background while it's open (`PhoneBackup.chatSizes`: every text's and picture message's words, and each photo's and video's size from `openFileDescriptor(…).statSize`; stops when the list closes, starts again when it opens). **Find a chat** (by name, or a number's digits); a **chip per type** the phone has, with how many (`ChatChoice.TYPES`: Conversations, Groups, Codes, Promotions & spam, Automated), and "N chats hidden: they won't be backed up"; a **sort** menu (newest or oldest first, most or fewest messages, largest or smallest, name; `ChatSort`); **Select all** (the chats shown); each chat's avatar, messages, size once known, "Group", last date and, on a line of its own, its kind. All start ticked, with the kinds Settings leaves out hidden. The bar has *N of M chats* (and their size) and **Done** (off with none chosen); Back and the arrow do the same, and none chosen goes back to how they started. What a backup is of is `ChatChoice.chosen`: the chats ticked, of a type not hidden, or null (an ordinary backup, `UiState.only`) when that's every chat but the kinds Settings leaves out; otherwise exactly those (`EXTRA_ONLY`).
- **Running** shows a backup the same way: messages, chats, photos so far, and the time left the backup works out itself.
- **Backup saved / updated / already up to date / stopped / didn't finish**: a line with the file's name and size (for an update, what it added), the file's counts, then notes (`Note`) for photos that couldn't be read, photos still to add if it was made without them, only some chats ("This backup has only the N chats you chose"; for an update, that the file's other chats are as they were), and for a file online that Drive shows it as 0 bytes until it has uploaded it; **Back up automatically** (a switch, except after a backup of only some chats: the automatic backup of this file, at the interval already set, else every day), "Next: your computer backup" (Settings → Tools → Bring in files…; after a new backup only), **Done** (the filled button) and **Share** (any app: Drive, email, Nearby Share).
- A banner on Welcome and Review says when this app is still the SMS app, with **Switch back**.

Estimates use speeds measured on the emulator (38,281 messages in 7½ minutes): 250 texts a second, 15 picture/group messages a second (each is several writes). Time left counts work the same way, since a chat's texts go quickly and its pictures slowly.

**The result is saved** (`RestoreState.save`, preferences `last_restore`): when Google Messages takes the SMS role back, Android revokes this app's SMS permissions and ends its process, so without it the app would reopen on Welcome instead of "You're all set". After a stop or failure the file is reopened too, quietly, so **Restore again** works.

## Backing up this phone (`PhoneBackup`)
Reading needs only `READ_SMS`, asked for at the time (with `READ_CONTACTS` for chat names, optional, and notifications), **not** the SMS role: the phone's SMS app is never changed. `READ_SMS` is a hard-restricted permission: Android grants it only to apps whose installer allowed it, which `adb install` and the phone's own installer for downloaded APKs do; Play would need a policy exemption.
- Chats come from `content://mms-sms/conversations?simple=true` (newest first), their people from `canonical-addresses`. **One canonical address can hold several numbers** (`5550100001;5550100002`, from a group text): `PhoneBackup.addrs` splits on `;` and `,` (and on spaces when every piece is a whole number), so they don't become one 20-digit "number". `addr` keeps digits and `+` for a number, lower case for an email address, and a business name as it is. Names, starred (Android's Favorites) and photo from `PhoneLookup`, else the number; the rest of the contact (`cardOf`: its `LOOKUP_KEY`, other numbers, emails, nickname, organization and title, birthday, labels from `Groups` that aren't auto-added or the system's, relations) from `ContactsContract.Data`, once per contact, into the person's `contact` (see [[Restore package]]); each thread's `people` records them, and a contact's photo goes into the package once (`contacts/<n>.jpg`), kept by later updates. Contacts are looked up again on every update, so a renamed or newly starred contact shows.
- Each chat: texts (`content://sms`, types 1 and 2: drafts and unsent ones are left out), then picture/group messages (`content://mms`, boxes 1 and 2) with their parts (`content://mms/<id>/part`: text, or a photo or video listed with its type, name and part ID, the SMIL layout part skipped) and sender (`/addr` type 137). Photos are then copied in (`copyParts`, through a temporary file so the tar header can have its size), or, without photos, left listed with no `file`. Sorted by time and written as one `threads/<nnnn>.ndjson`; the manifest goes last, so a stopped backup is a whole file of the chats finished so far. A new backup that fails deletes its file.
- **Updating a backup** (`previous` set): new entries are written from `RestorePackage.end` (over the end blocks) and the file is cut to its new length. Chats are matched by their sorted addresses. For a chat the file has, the phone's messages up to its `last` are counted; if there are no more than the file has and no photos are wanted that it lacks, only messages after `last` are read and written as one more piece (`threads/<nnnn>.<k>.ndjson`, listed in `files`); otherwise the whole chat is read and merged with the file's (same message: same date, box and text; the file's photos are reused by position, its first `src_id` kept, a message deleted from the phone kept) and written again under its first name. Each thread entry keeps `messages`, `sms`, `mms`, `first`, `last`, `media`, `media_waiting`, `media_bytes`, so the next update needn't read it; a file from before these were kept is read once to work them out. The manifest gets `updated_at` and a `history` entry per run.
- **Size**: each chat's file is gzipped (`addThread`, format version 3), a photo already in the file byte for byte is pointed at rather than copied again (`copyMedia`: same size, then SHA-256 via `digestOf`), the manifest is written without indentation with the last 100 runs of `history`, and a file the app owns is compacted after an update once unused entries are a quarter of it (`BackupFiles.compact`; see [[Restore package]]). On the emulator a whole backup went from 6.3 MB to 0.45 MB and from about 2½ minutes to 62 s; three updates in a row left one manifest and no unused bytes.
- **Where it's written** (`BackupFiles.run`): in place when the file can be opened `"rw"` and isn't a pipe (`statSize` ≥ 0): reads through a `FileInputStream` channel and writes through a `FileOutputStream` channel on the same descriptor. Otherwise (Google Drive) the file is updated through a copy and written back with `"wt"` (or `"w"`): for the automatic backup's file, its **copy on the phone** (`PhoneCopy`, `noBackupFilesDir/backup-copy.tar`, on unless Settings → **Keep a copy on this phone** is off: `Setup.keepCopy`, pref `copy`), else a download to the cache deleted afterwards. The copy is made from the Drive file at the first run (not rebuilt from the phone: the backup keeps messages deleted from the phone since), updated in place like a file on the phone, uploaded whole, and marked as the copy of that uri (prefs `phone_copy`) only after a run that worked, even if the upload then failed (the next run adds to it and uploads it again). With a copy the Drive file is never read back. It's deleted when the automatic backup moves to another file, is turned off, or the switch is; and after a run that leaves less than a tenth of the phone's storage (at least 1 GB) free (`StorageManager.getAllocatableBytes`), which Settings shows. A copy isn't started on a phone already below that (`PhoneCopy.wanted`): the run goes the old way. A full phone (`ENOSPC`, `BackupFiles.isFull`) stops the backup, even while copying a photo (it isn't counted as a photo that couldn't be read), and is said in words (`BackupFiles.why`, with the free space the phone's settings show). On failure nothing is left behind: a whole backup cut short deletes its copy, temporary files are deleted, a new file is deleted (`RestoreService`; never the automatic backup's file: its failed run is recorded instead, `Daily.record`, and turning automatic backup on runs its first backup as an automatic run, so a new file that fails is emptied, not deleted), and the automatic backup's empty file, written whole and cut short, is emptied again so the next run starts over (it used to be left as a file that isn't a backup). Each whole write to a file online (new, or through the copy) is recorded in preferences `backup_files` (uri → bytes and time). An update that finds its file empty writes a whole backup, unless that record says this app wrote it less than a day ago: then the Drive app hasn't uploaded it yet ([[Gotchas]]), so the run stops with that message (no second whole backup queued behind the first); after a day it's written whole again, in case that upload was lost.
- **By itself** (`Daily`): a `JobScheduler` periodic job (every `everyHours`, 1 to 720, with a quarter of that as flex and at least 15 minutes; App Standby may run it less often for an app not opened in a while, battery not low, optionally charging, optionally unmetered network, on by default for a file not on the phone's own storage; kept across restarts) runs `DailyBackupService`, an update of the chosen file with its photos setting. A file that's still empty (just chosen) gets a whole backup. With **Tell me after each backup**, a quiet notification says what was added. A run Android stops (about 10 minutes) writes what it has and carries on next time. **An updates file for a backup online** (`Setup.updatesUri`, Settings → "Upload less: a small updates file" → **Set up…**, a `CreateDocument` beside it, `Daily.useUpdates`, then a run at once so it isn't left an empty file): Drive can't add to a file, so a run would download, rewrite and upload the whole backup. `Daily.run` (the job and "Back up now", via `RestoreService` `EXTRA_AUTO`) instead writes, over the updates file, a whole new package of every message after the big file's last catch-up minus two days (`BackupFiles.writeUpdates` → `PhoneBackup(since = …)`; the manifest says `updates_since` and `updates_for`). The big file catches up (the usual update, then the updates file starts again) once the updates uploaded since add up to its size (`base_bytes`, `updates_sum`: about the cheapest point to rewrite it), or after 90 days, or when there's no record of its last catch-up. Prefs `base_at`, `base_bytes`, `updates_sum`, `updates_msgs`/`updates_media` (to report what's new since the last run). Restoring or importing: the big file, then the updates file (duplicates are skipped). Live test: 19 KB written instead of 7.6 GB. Waiting for Wi-Fi needs `ACCESS_NETWORK_STATE` (declared; it only reports whether there's a network). If Android refuses a schedule anyway, `Daily.enable` records the error for the first screen instead of crashing, and `Daily.ensureScheduled` (on every return to the app) schedules it again when it's on but nothing is pending. The last run (time, added, error) is in preferences `daily_backup`; a failure notifies. A manual update of the same file counts as the day's run.
- The format is the extension's (see [[Restore package]]), with `tool: "Message Archivist"`, `owner.number` (`RestoreService.ownNumber`, when the phone knows it: the extension keeps a second number's texts apart), `source: "phone"`, each chat's `names`, exact times, and `src_id` `sms:<id>` / `mms:<id>`. So it restores with this app on any phone.
- Numbers are shown as the extension shows them (`RestoreService.shown`, the same rule as `GMLib.formatNumber`): a North American number as "(555) 010-0001", another with a country code as "+44 7700 900 123"-style groups, a name or anything else as it is; a chat title of several numbers is formatted number by number. Used for the chat on the progress screen and in notifications, and the restore review's chat list.
- **Other apps' exports** (`PhoneBackup.exports`): after the chats, each export waiting on the phone that the file doesn't have goes in as `exports/<n>/<k>.<ext>`, and the manifest's `exports` lists the file's own and the new ones ([[Restore package]] → Exports); a stopped run leaves them waiting. `Result.exports` says which went in; `BackupFiles.run`, once a run to a backup file has worked (new, in place, through a copy or the phone copy), marks them `Exports.written`, so their copies go. An updates file carries the waiting ones each time, until the big file catches up. The done screen says how many went in.
- **Every contact** (Settings → *Contacts* → *Save all my contacts*, off at first): each run reads the whole address book (`ContactBook.all`: those with a number or email address) and, when it differs from the file's copy, writes it as `address-book.json.gz` with `address_book` in the manifest; turned off, a file that had one gets an empty one. See [[Restore package]].
- **Left out** (Settings → *Leave out of phone backups*, `Clutter.chosen`): before a chat is written, `kindOf` judges it as the extension does ([[Sources]] → Kept apart): one-to-one only, never a starred contact; who it's with from its address and contact name (`Clutter.senderOf`); two counts of your sent texts and picture messages first, and a chat with three of yours (one, to a contact) isn't read further; otherwise every text's body and picture message's words (`mmsText`) go through `Clutter.traits`, over the whole chat, not only what's new. A chat to leave out isn't written (its messages still count for the progress), a file that had it drops it from its manifest (its old pieces stay unused), and the manifest records `left_out` by kind ([[Restore package]]). `Result.leftOut` shows on the done screen ("Left out as codes, promotions or automated texts (Settings): N chats"), the review screen says what will be left out, and the log line ends `leftOut=N`. Updates files and automatic backups go through the same loop.
- **Only some chats** (`only`: the chosen chats' keys, their sorted addresses, from the screen as `EXTRA_ONLY`): only those are read and written. A new file holds just them; an update brings just them up to date and carries the file's other chats over from its manifest as they were. They aren't judged for leaving out: choosing one is asking for it. Progress counts only theirs (`smsIn`/`mmsIn` per chat, not `summary`); the run's `history` entry has `chosen` ([[Restore package]]); `Result.chosen` shows on the done screen and the log line ends `chosen=N`. Such a run isn't the automatic backup's (`Daily.record` is skipped, so the next automatic run still comes), and automatic runs and updates files are always of every chat.
- Time left: texts and picture messages are timed apart as they're read (picture messages take several reads each), then each kind's remainder at its own speed.
- **RCS**: Google Messages keeps RCS chats in the same database as MMS, so they're backed up, except that since mid-2026 a Google bug stops some **outgoing** RCS messages being stored there (see [[Android direct connection]]). Those are only in a backup made with the extension. The extension imports these files into its library (Settings → Tools → **Bring in files…**).

Measured on the emulator: 38,281 messages, 4,741 of them picture/group, 262 photos, in about 2½ minutes (50 s without photos); restoring that backup elsewhere gives back every message and photo exactly (`test/restore/compare.mjs` checks two packages chat by chat). Updating the photo-less backup with photos: 57 s, 0 messages and 262 photos added, the result identical to a backup made with photos. A daily update with two new texts: 2 s, the file 9 KB bigger.

## How messages go in (`Restorer`)
- Thread id from `Telephony.Threads.getOrCreateThreadId(addresses)`.
- SMS: `bulkInsert` into `content://sms`, 400 at a time: address, body, date, date_sent, type (1/2), read, seen.
- MMS: insert into `content://mms` (date in **seconds**, msg_box, m_type 128 sent / 132 received, `ct_t` multipart/related), then parts into `content://mms/<id>/part` (text part with `text`; file parts by streaming into `openOutputStream(partUri)`), then addresses into `content://mms/<id>/addr`: 137 = from (`insert-address-token` for sent), 151 = to.
- **Received group messages also list this phone's own number as a 151.** Without it, Google Messages files each received group message as a one-to-one chat with its sender (seen on the emulator). The number comes from `SubscriptionManager.getPhoneNumber` or `TelephonyManager.line1Number` (allowed for the default SMS app), or the user types it.
- Duplicates: before starting, every `thread|date|type` (SMS) and `thread|seconds|box` (MMS) on the phone is loaded; matching messages are skipped. Restoring twice adds nothing; a stopped restore carries on.

## Building and testing
```bash
cd android && JAVA_HOME=$(/usr/libexec/java_home -v 17 2>/dev/null || echo /opt/homebrew/opt/openjdk@17) ./gradlew assembleDebug
```
APK: `android/app/build/outputs/apk/debug/app-debug.apk`. CI builds it, lints it and runs the unit tests on every push (`.github/workflows/ci.yml`, job `android`: `assembleDebug lintDebug testDebugUnitTest`). Emulator testing: [[Testing]].

**Toolchain** (after 0.0.1.0, from Dependabot): Android Gradle Plugin 9.4, Kotlin 2.4, Compose BOM 2026.09. AGP 9 compiles Kotlin itself, so there's no `org.jetbrains.kotlin.android` plugin (applying it fails the build) and no `kotlinOptions` (the JVM target follows `compileOptions`). That Compose needs `compileSdk = 37`; `targetSdk` stays 35, so the app behaves the same on phones. Lint passes but now reports 45 warnings, mostly style (`UseKtx`, `AutoboxingStateCreation`, plurals); none fail the build.

**Unit tests** (`./gradlew testDebugUnitTest`, `app/src/test/`): `AppsTest` checks `Apps.detect` and `Apps.title` on made-up names and zips, and that each app's name, letters and colour are its module's in `extension/modules/` (found by walking up from where Gradle runs it). `ChatChoiceTest` checks which chats a backup of chosen chats is of (`ChatChoice.chosen`: ticked, hidden types, as the list starts). `ClutterTest` runs `Clutter` on `test/filters/cases.json` (found by walking up from where Gradle runs it), the cases the extension's `test/filters/run.mjs` checks `GMLib` against, so the app and the archive leave out the same chats. Change a rule in one and the other's test fails until it's changed too. `junit` and `org.json` (a real one: Android's is only a stub in unit tests) are test-only dependencies.

Debug builds accept `--es restore_path <file the app can read> --ez auto true` to start a restore without the file picker, and `--es backup_path <file the app can write>` (optionally `--ez media false`, `--ez update true`, and `--esa only <keys>` for only those chats: a key is the chat's addresses sorted and joined with commas, so a group's commas are written `\,`, which `am` keeps and the hook takes out) to back up, or update that file, at once (tests only); release builds ignore both. `adb shell cmd jobscheduler run -f io.github.trikhster.messagearchivist 7` runs the daily backup now.

## Known limits
- Times in a file from the extension are to the minute (from Google Messages for Web); a phone backup's are exact. RCS goes back as SMS/MMS; picture messages arriving mid-restore aren't downloaded (see `MmsReceiver`).
- The launcher label is cut to "Message Ar…" on most launchers.
- Not on Google Play: people sideload the release APK from GitHub Releases, signed with the project's key (see [[Releasing]]). CI's debug APKs have a different signature, so one can't update the other.
