# Settings page (`options.html`, `options.js`)

The extension's options page. Unlike the content script, it can read and write the backup folder directly (it's an extension page), using `folderForReading()` and `libraryIO(dir)` (which also hashes what it writes). Loads `zip.js` and `library.js` too.

## Tabs and routes (0.5.0.0)
**One menu down the left** (`<aside class="rail">`, its `nav.tabs`): the logo and version, then **Archive** (Chats, People, Contacts, Search, Media, Review, Analysis, About: buttons with `data-tab="archive"` and `data-view`, the viewer's own names for its views) and **Manage** (Home, Backups, Phone restore, Tools, Settings, Apps: `data-tab`), the theme switch (and the app's install button) at the bottom. Its own shade (`--surface-1`) and a line down its edge (`--outline-variant`) set it apart from the page. **☰** (`#menuBtn`, `collapseMenu`) collapses it to a 72px strip of icons, the group names becoming thin lines and each entry's name its tooltip; remembered in localStorage (`ma-menu`), and applied before `menu-ready` turns the width animation on, so a page opening collapsed doesn't animate. Below 800px it becomes a row at the top that scrolls sideways, and collapsed is just the title bar. A `data-view` button opens that view in the archive frame (`VIEW_HASH` maps `chats` → `#chat`, `stats` → `#stats/all`); the viewer posts `ma-view` on every route, so `markMenu()` lights the view it's on, including one reached inside it (a contact's circle → People). Before this, Settings had a tab row and the archive its own row below it (the owner: "there has to be a better way to organize these menus").

`#archive` (the viewer in a frame, `viewer.html?library=1&embedded=1`: the tab Settings opens on when the address names none and there's a folder; `#archive/<viewer address>` opens it there, e.g. `#archive/chat-id/<id>`, `#archive/contacts`), `#home` (with the setup steps until there's a folder: folder, **start with your phone** (`welcomePhone` opens Tools and the phone import), Google Messages, back up everything; `#welcome` on first install keeps them showing), `#backups` (the index of every chat), `#restore` (phone restore file), `#tools` (checks, import, past runs), `#settings` (Basic / Advanced, remembered in localStorage). `openArchive(hash)` loads the frame the first time and again after the backup changed (`archiveStale`: a run recorded in `runs`, a new folder), else just sets its hash; Open my backup, a row's ⋯ → Open in my backup and the People matches link use it. The frame asks for a tab by posting `ma-settings` (`#delete:<folder>` → Backups and the delete dialog). With the Archive tab showing, `body.archive-on` lets `main` go full width and the frame fills the window below the tabs. `#folder` opens Settings at the folder, `#delete:<folder>` opens Backups with the delete dialog. `showTab()` swaps the panel and `refreshTab()` draws only what that tab shows.

## Reading the backup once
`getLib(force)` reads `data.js`, `backup-state.json` and which chat folders exist, once, and Home, Backups and Phone restore share it. It's dropped (`libCache = null`) when something on disk changed: a run finished (`runs` changed), a delete, an import, a clean-up, a new folder, access allowed. `chrome.storage.onChanged` only reacts to `settings` and `runs`, in batches of 300 ms: settings redraw from memory; `runs` re-reads the backup. (0.4.x redrew everything, including 30 full logs, on every storage change.) Past runs put a log on the page only when it's opened.

## Order of chats and people
Settings tab (Basic), before Theme: `chatSort` ([[Storage and settings]]). The Backups tab has its own **sort menu** (`#indexSort`: Favorites then A–Z, Most recent message, Most messages) that starts at it (`auto` → A–Z); `renderForm` resets the menu only when the setting itself changed, so other settings saving doesn't undo a choice made in the menu. The viewer reads the same setting ([[Viewer]]).

The index's table wraps long unbroken text anywhere (`#index td { overflow-wrap: anywhere }`): a handle, an email address or a chat's folder path in its details row used to push the table past the card and scroll the page sideways.

## Leave out of your archive
Settings tab (Basic), after the backup folder: `skipCodes`, `skipPromos`, `skipAutomated` ([[Sources]] → Kept apart). Imports skip such chats in `importChat` (judged on the library's messages and the incoming ones together, with `labels.json`), count them in `report.left` and say so in the summary and the log. **Find the ones already in my archive…** (`skipFind`) looks through every row (its `traits`, or its `messages.json` for a row from before them), lists what it found, and **Move them out of my archive** (`skipGo`) moves each folder into `removed-chats/<date>/` (keeping app folders: `WhatsApp/<chat>`), adds them to `backup-state.json` `excluded` with the `reason`, takes them off the backup list, and ends with `finishLibraryRun` (kind `leave out`). The extension's "Back up everything" does its part in `content.js` ([[Backup run]]).

`saveSettings` saves one change at a time (a promise chain): each reads the settings and writes them back, so two switches flipped together lost the first.

## In the app
`const APP = !!window.MA_APP` ([[App]]): rows can't run backups (`canRun`), the *By itself* cells are `ext-only`, Home's and the index's empty states point to Bring in files and the extension, `MA_APP.onFiles` hands phone backups opened with the app to `importAnything(false, handles)`, `finishLibraryRun` copies the viewer from `MA_APP.archiveURL` (the extension's own), and `hashchange` also handles `#delete:` and `#folder`. In `options.html`, `ext-only` marks what needs Google Messages (setup steps 2–3, Back up everything, the backup list's tools, the fix bar, the extension's backup settings) and `app-only` the app's wording.

## Patterns
- Anything that writes the library goes through `libraryIO` (`readText`, `exists`, `write`, `remove`, `hashes`, `dir`) and ends with `finishLibraryRun()`, which rewrites `data.js`, `export-info.json`, `verification.json`, `messages.csv`, the Obsidian notes (when they're on), a log and `SHA256SUMS.txt`, and records the run in Past runs. `refetchMissing` is lighter: it rewrites the affected `messages.json` and the checksum list, then starts a fetch run.
- Actions that need the Messages page go through the [[Background worker]]: `gm-run-now` (backup-list jobs) or `gm-to-tab` (`gm-media`, `gm-total`, `gm-list-chats`).
- `toast(text)` for short confirmations; `esc()` for anything put into HTML.
