# Known issues

From a code review of 0.4.5.0 (2026-10-26). Bugs first, then tech debt, then ideas. Strike through or delete an item when it's fixed, and say in which version.

## Bugs
All four found in the 0.4.5.0 review were fixed before 0.4.5.0 was released (kept here for the record).

1. ~~**Popup photo counts go stale after Fetch photos, Upgrade to full size, and scheduled runs.** `runScheduled()` (`content.js`) calls `finishRun()` with `{ ok, summary, added }` and no `perChat`, so `gm-backup-status` is never sent and `chatStatus[id].media` keeps the counts from the last manual backup. The popup then offers "Fetch N photos" again for photos already fetched. *Fix*: pass `perChat` (built from `results`) to `finishRun`, or report `gm-backup-status` from `runScheduled`.~~ **Fixed in 0.4.5.0**: `runScheduled` passes `perChat` to `finishRun`; scheduled runs send it with `statusOnly`, so only `chatStatus` changes and `runDue` keeps updating the backup list.
2. ~~**End-of-run text points to an option that's gone.** `folderRun()`'s summary says "“Retry failed photos” (popup → More options) tries again", but 0.4.5.0 removed that checkbox (the popup's **Fetch photos** retries failed ones). *Fix*: "“Fetch photos” in the popup, or “Retry failed photos” in Settings, tries again."~~ **Fixed in 0.4.5.0** with that wording.
3. ~~**The popup says "Fetching…" even when the page is busy.** `runPhotos()` in `popup.js` ignores the reply. A busy page answers at once with "An export is already running", but the popup shows "Fetching…" anyway and closes. (A successful run only answers when it ends, so the reply can't simply be awaited.) *Fix*: `gm-ping` first and check `running`, or wait a moment for an early error.~~ **Fixed in 0.4.5.0**: both. The popup pings first, then waits 600 ms for an early refusal.
4. ~~**Speed-run chats show as "Partly backed up" on the backup list.** `gm-backup-status` in `background.js` writes `lastResult` from `complete` only, without knowing the `messages` status.~~ **Fixed in 0.4.5.0**: `lastResult` and `runScheduled`'s summary say "Messages backed up, photos to fetch" (no "Run again to carry on").
5. **The app's restore estimate of time left starts too high on a slower run.** On the emulator it said "About 14 minutes left" at 18%; the whole restore took 7 min 38 s. Probably because the estimate weighs each picture/group message as a fixed 16.7 texts (`SMS_PER_SEC / MMS_PER_SEC`, measured on the emulator), so a run whose texts go slower than the emulator's, or whose picture messages go faster, is over-estimated. *Fix*: time the two kinds apart as the restore goes, as the backup does (`PhoneBackup.secondsLeft`), and estimate each kind's remainder at its own measured speed. The README says the estimate is a guide.
6. ~~**The app crashed turning on automatic backup to a file online** (Google Drive), or on turning on **Only on Wi-Fi**: Android 14 and later refuse a job with a network constraint from an app without `ACCESS_NETWORK_STATE` (a `SecurityException` from `JobScheduler.schedule`). Found in the live test on a Pixel (Android 17); every emulator test had used a file on the phone, so no network constraint.~~ **Fixed** (after 0.0.1.0): the permission is declared; `Daily.enable` catches a refused schedule and shows it as "The last backup didn't work"; `Daily.ensureScheduled` puts back a missing schedule when the app opens (the crash had left the setting on with nothing scheduled).
7. ~~**Turning on "Back up automatically" after a backup reset the other automatic-backup settings**: how often, charging, Wi-Fi and notifications went back to their defaults.~~ **Fixed** (after 0.0.1.0): `setDaily` keeps them, as `startAuto` did.
8. ~~**Settings showed other apps' chats as "Folder missing"**: the check listed only `conversations/<chat>`, not `conversations/<App>/<chat>`.~~ **Fixed**: app folders are looked into.
9. ~~**"That isn't a phone backup… (it has no manifest)" for an empty file**: a Google Drive download that hadn't finished (0 bytes) got the same message as a wrong file.~~ **Fixed**: `readPackage` says what's wrong (empty, cut short, not a tar backup).
10. ~~**0-byte backup files on Google Drive, and the whole backup made again for each.** Drive shows a file the app wrote as 0 bytes until the Drive app uploads it, which can take a long time on some networks ([[Gotchas]]). An update that then read the file back found it empty, took it for a file never written and made the whole backup again (every message and photo), queuing one more upload behind the stuck one. The updates file also stayed 0 bytes from **Set up…** until the next scheduled run. Seen on a Pixel after 0.0.1.0.~~ **Fixed** (after 0.0.1.0): `BackupFiles.notUploadedYet` stops such a run for a day, saying the last backup hasn't been uploaded yet; the updates file is written as soon as it's set up; the done screen says Drive shows 0 bytes until it has uploaded the file. Then the phone copy (`PhoneCopy`): with it a run never reads the Drive file back, so a pending upload is simply replaced by the next one.

11. ~~**A first backup to Google Drive with photos ran out of space** ("write failed: ENOSPC"): the new phone copy needs room for the whole backup, and the live phone had 3% free. The cut-short automatic backup file was also left as a file that isn't a backup.~~ **Fixed** (after 0.0.1.0): no copy is started on a phone below a tenth free (at least 1 GB); a full phone stops the backup with a plain message (also while copying a photo, which used to be counted as unreadable); the cut-short file is emptied again. Checked on the emulator with the disk filled: nothing left in the app's storage. Still: a backup with photos needs room for the whole file somewhere on the phone (Drive's app keeps an upload on the phone too), so on a nearly full phone only one without photos fits.
16. ~~**Month notes linked photo days the photo notes didn't show**: a day's photos were counted from every file, but a chat's photo list kept only its newest 3,000, so the live vault had 275 links to headings that weren't there.~~ **Fixed** (unreleased, notes version 4): a chat keeps its newest 10,000, and a day's photos are linked only when the photo notes show that day.
15. ~~**Changing the notes' version left the old notes behind**: `update` dropped the old manifest's list of notes on a version change, so nothing it had made could be removed; the live vault was left with 1,279 stray person, chat and message notes.~~ **Fixed** (unreleased): the list is kept and only the chats' analysis is dropped, so notes no longer made still go (tested). The strays were removed by hand, after checking each was the tool's own and unedited.
14. ~~**A backup from Google Messages dropped a chat's starred contact**: `saveContact` wrote the card from the page alone, losing `favorite` from a phone backup.~~ **Fixed** (unreleased): it keeps `favorite`, the phone's contact (`card`) and a photo the page lacks.
13. ~~**A group member matched everyone with their name**: `groupsOf` keyed each group member by number *and* name, so a group with a numbered "Sam" was listed under every Sam in People (seen live: groups of 3 linked 4 people), and the Obsidian notes connected them all.~~ **Fixed** (unreleased): a member with a number, email or handle is matched by that only; by name only when the group knows nothing else about them.
13. ~~**The app crashed on Back up now after the backup file was deleted or replaced on Google Drive**, and the automatic backup's notification showed Android's "UID … does not have permission to content://…". Deleting a document takes away the app's permission to it, and passing that uri to the service (`startForegroundService` with grant flags) throws `SecurityException` on the main thread. Seen on the live Pixel.~~ **Fixed** (after 0.0.1.0): `startBackup` catches it; a `SecurityException` or `FileNotFoundException` anywhere in a backup is said in words (`BackupFiles.isGone`, `GONE`: choose the file again in Settings → Backup file → Change). Checked on the emulator with the automatic backup pointed at a file it had no permission to: no crash, the message on screen and as the job's recorded error.
14. ~~**The automatic backup's file online was deleted by its own first run when that failed, and every run after it failed.** Turning automatic backup on with **New file…** started the first backup as an ordinary new backup; a new backup that fails deletes its file (`RestoreService`), but the automatic backup still pointed at it, so Back up now crashed (before 13's fix) or said the file was gone, and making another new file repeated it (seen live: seven Drive files made in a day). The failed run wasn't recorded either, so the first screen still showed the run before it that worked.~~ **Fixed** (after 0.0.1.0): `startAuto` runs the first backup as an automatic run (`Daily.run`: an empty file is written whole and emptied again if that fails), and `RestoreService` never deletes the automatic backup's file and records a failed run of it (`Daily.record`), so the first screen says it didn't work.
15. ~~**Every one-to-one WhatsApp chat exported from Android came in as a group**, asking "Which one is you?" and, if skipped, showing none of your messages as yours: any line without a sender made a group, and Android's "Messages and calls are end-to-end encrypted" notice has none in one-to-one chats too.~~ **Fixed** (unreleased): a group is more than two people, a group's notice, or two people in a chat named for neither ([[Importers]]).
16. ~~**An iPhone's WhatsApp notices came in as messages**: from the contact ("end-to-end encrypted", "security code changed") or from the group's own name, which also counted as a person in the group.~~ **Fixed** (unreleased): a marked line under a group's own name, or saying what only WhatsApp says, is a notice.
12. **The backup's time left is too low on a big phone** (live: 12 minutes left at 49%, still 15% to go 18 minutes later, though the phone was filling up). Measure on a run with room before changing `PhoneBackup.secondsLeft`.

## Tech debt
- ~~**`gm-fetch` sends media as base64 over runtime messaging**~~ **Mostly fixed in 0.5.0.0**: during backups the [[Writer frame]] fetches and returns a Blob. `gm-fetch` remains the fallback (date-range zips, contact cards before a backup starts), with its 48 MB limit.
- **Two key schemes in the viewer**: labels use `chatKey(c) = id || folder || title`; flags use `flagKey(m) = (id || ci)|(msgId || index)`. `ci` is a position in `data.js` and changes when chats are added or removed, so a flag on a chat without an ID can move to another chat. Unify on `chatKey` with a one-time migration in `labels.json`.
- **Photo status rules exist twice**: `GMLib.mediaStatus()` and the viewer's `mediaSt()`. The viewer could load `library.js` (copy it into the folder with the viewer files) instead.
- ~~**Five copies of `getSettings()` with different defaults**~~ **Fixed in 0.5.0.0**: `GMLib.normalizeSettings()` everywhere.
- **Selectors outside `SEL`**: image parts, reactions, status, link previews, spinner, the Details page and the photo viewer are queried inline. Move them into `SEL` so a layout change is a one-place fix. See [[Google Messages page]].
- **`backupConversation()` is ~400 lines of closures** sharing state. Splitting it into stages (load, targets, journal/saving, fetching, finish) with an explicit state object would make it safer to change.
- **`content.js` is 3,000+ lines.** It could be several content scripts listed in the manifest (HUD, page reading, media, library writing), still with no build step.
- **"Fetch the missing ones again" ignores journal pieces.** If a crash left `journal/` pieces for that chat, `loadEntry()` replays them over the edited `messages.json` and could bring back the missing file's record. Rare; check for `journal/` first.
- **Upgraded file names end in ` (2)`.** Remove the thumbnail before writing the full-size file (or rename after) to keep the base name.

- **With full-size photos, a duplicate picture in a message can be saved twice.** `dropSamePictures()` only compares pictures saved together in `writeMessageMedia`; photos saved one at a time (full size between batches, `fetchTarget`) aren't compared with what's already saved for that message. On the mock chat: 2 extra thumbnails, the same in 4.6 with full size on. 0.5.0.0 makes full size the default, so it's more visible. Tools → Find duplicate photos cleans them up. *Fix*: before writing a single picture, fingerprint it against the message's saved pictures.
- **The viewer reads every chat when it opens** (all `chat.js` files, then indexes every message for search). 4.7 s for 408,000 messages; loading a chat's messages only when opened (and search on demand) would make it near-instant.

- **The Android app can't download a picture message that arrives during a restore** (it would need a full MMS stack). It notifies; Google Messages usually fetches it once it's the default again, but not always. Restoring when no messages are expected avoids it.
- **A phone backup can lack outgoing RCS messages**: since mid-2026 Google Messages doesn't always store them in the phone's database ([[Android direct connection]]). The extension's backups have them.
- **A chat that came only from a phone backup can get a second folder** when it's later backed up from Google Messages for Web, if the phone named it from its contacts and the web shows a different name (a number-named chat is found by its number). Renaming the folder's chat to the web's name avoids it.
- **A phone message whose photo and caption the web shows apart, backed up from the phone without photos:** its photo isn't fetched from the web (the photo half's ID is only in `also_ids`); updating the phone backup with photos and bringing it in again fills it.
- ~~**Phone backup files aren't compacted.** An update that writes a chat again in full (photos added to a backup made without them) leaves the old copy in the file, unused; so does each run's old manifest.~~ **Mostly fixed** (after 0.0.1.0): a file the app owns (the phone copy, a download for one run) is compacted once unused entries are a quarter of it ([[Restore package]]); the manifest is written compact with the last 100 runs of history. Still: a backup file kept on the phone itself isn't compacted (it can't be replaced in one step), and a backup made before version 3 keeps its plain (uncompressed) chats until it's made again.
- **A daily backup to Google Drive re-uploads the whole file** each day (Drive can't add to a file in place), unless it uses an updates file. Since the phone copy it no longer downloads it first.
- ~~**Pinned chats: the selector isn't checked against the live page yet** (`SEL.pinned`).~~ **Checked 2026-10-27**: on the live chat list a pinned item carries `data-e2e-is-pinned="true"` and a "Pinned" aria-label (both matched every pinned chat, and only those); the pin-icon and title forms matched nothing and stay as fallbacks.
- **A phone backup made before 0.5.0.0's address fix** can have a chat whose "number" is several numbers stuck together (17+ digits). Make a new phone backup; updating the old file keeps that chat beside the corrected one.
- **Contact photos from the phone** weren't tested on the emulator (its test contact had none); starred contacts were.
- ~~**The app is debug-signed.** Updating from a copy built on another computer fails ("App not installed") until releases are signed with one key.~~ **Fixed in 0.0.1.0**: releases carry an APK signed with the project's key; see [[Releasing]].

## The app (unreleased)
- **The app can't back up Google Messages** or start the extension's backups: "Back up everything", the backup list and photo fetching stay in the extension. Phase 2 of [[Desktop app]] (`externally_connectable`) would let the app start and follow them.
- **Settings, past runs and the Obsidian switch are the app's own**, separate from the extension's (each origin has its own storage); only the backup folder is shared. The archive's `logs/` has every run of both.
- **Two writers, no lock yet:** an import or delete in the app while the extension's backup runs could leave one of them out of the index until the next run rewrites it. The same is true of the extension's own Settings today. Phase 0's `archive.lock` ([[Desktop app]]) is the fix. In the app, deleting a chat can't check whether a backup is running.
- **Not yet tried:** installing it for real (the check: Chrome reports it installable, with no manifest errors), opening a `.tar` from Finder or Explorer (the same import is tested by handing it a file), and Edge.

## Codes, promotions and automated texts (unreleased)
- **The words are mostly English** (with a few other languages' words for "code"): codes and promotions in other languages are found less often; their chats may land in Automated (from a short code or sender ID) or stay in All chats.
- **A business saved as a contact** counts as a contact: it needs more to be called codes or promotions, and is never Automated.
- **A chat new to the archive** in "Back up everything" is read once before it can be judged and taken back out (the conversation list shows only names).
- ~~**The Android app's own phone backups** still hold every text, codes included.~~ **Done (unreleased)**: the app has the same switches (Settings → *Leave out of phone backups*).
- ~~**Opt-out lines in other spellings** ("STOP=end", "Stop2End", "Rply STOP", "HELP4help", "4 msgs/mo") weren't recognised, so those chats stayed in All chats.~~ **Done (unreleased)**: matched in any capitals, in the archive and on the phone; chats already in an archive are counted again when leaving chats out (`TRAITS_VERSION`). Promotions without any such line, no link and a sender that writes like a person still aren't caught: there's nothing reliable to go on.
- **The rules exist twice**, in `extension/library.js` and `android/.../Clutter.kt`. `test/filters/cases.json` keeps them giving the same answers; a change to one needs the same change in the other and a case for it.
- **The phone's switches are its own**: the app, the extension and the installable app each keep their own choice.
- **In the app, the Leave out switches are the app's own** (separate storage), for what's brought in there; the extension's govern its backups.

## Missing
- ~~**A big backup kept on Google Drive is heavy to keep up to date.** Drive can't add to a file, so each automatic run copied the whole file to the phone's cache, added what's new and uploaded it whole (the live test's backup with photos was 7.6 GB).~~ **Mostly fixed** (after 0.0.1.0): an optional updates file beside it ([[Android app]], `Daily.run`); the first live run wrote 19 KB instead of 7.6 GB. Still: a catch-up of the big file uploads it whole (rarely), and restoring takes two files. Since the phone copy (`PhoneCopy`) a catch-up no longer downloads it first; the copy keeps that room in use on the phone (Settings shows how much, and turning it off frees it). The updates file isn't offered by default; Settings suggests it.
- **iMessage isn't importable yet.** Its database (`~/Library/Messages/chat.db`) is SQLite; reading it needs a small SQLite reader (plain JS, no dependencies), the `attributedBody` text of newer messages, `chat.db-wal` for the newest, and the Attachments folder. Signal has no plain export. See [[Sources]].
- ~~**People are matched across apps by number or name only.**~~ **Done (unreleased)**: People ([[Sources]] → People) joins chats that share a number, email or app handle, suggests same-named ones, and lets the owner join, split, rename and keep apart by hand (`people.json`).
- **Instagram and Messenger chats join someone only by hand or by a suggestion**: their exports have names, no numbers or user IDs. WhatsApp chats with saved contacts likewise (the export has the contact's name only).
- **A person's groups across apps** are found by number, email or handle, or by name only within the same app (and only for members the group has no number or handle for); a group in one app isn't matched by a name from another.
- **Obsidian notes after a delete or clean-up in Settings** are brought up to date only when "Keep them up to date" is on; otherwise at the next *Update the notes*. Notes for chats removed from the archive are removed then, unless the owner wrote in them.
- **The Obsidian update at the end of a backup from Google Messages** (`writeIndex` in `content.js`) goes through the writer frame; it was tested through Settings and Node, not yet on a live backup run.
- **The address book isn't shown in the viewer yet**: People joins and names people with it, but a person's page doesn't list their work, birthday or labels (the Obsidian notes do). Its photos aren't saved either, only those of contacts in chats.
- **What the Obsidian notes work out is English-leaning**: the stopwords, the everyday words that are also first names (`AMBIG`) and the phrases events are found by are English (with a few other languages' birthday and holiday wishes), so in other languages common words can show up as topics and events are missed. Mentions count a first name only when no one else in People has it, so two Sams are never mentioned.
- **Events are guesses**: "on my way" can be on the way home, not to meet; "congratulations" picks up the day's words for what for ("baby?") even when the chat was about something else; "landed" needs "just", "we" or "in" before or after it, and a trip's place is only taken after "landed in", "trip to" and the like. Each event says it's likely and links to its day.
- **Phrases rarely match between people word for word**, so most phrase topics stay on one person's note; topic notes are mostly words (live: 63 topics, 1 of them a phrase).
- **A group's senders are matched to people by number, or by name when that's one of the group's people**; a sender known only by a name that isn't is shown by that name.
- **People's names in Obsidian follow the People tab**: renaming a person renames their note (links in the generated notes follow; links the owner typed in other notes to the old name don't).
- **WhatsApp exports are capped** by WhatsApp (tens of thousands of messages, fewer with media); a longer chat comes in partly. Bringing in a later export adds what's new, not what WhatsApp left out.
- **WhatsApp's notice words are mostly English** (`NOTICE`, `GROUP_NOTICE` in `whatsapp.js`, with "end-to-end encrypted" and "created group" in a few other languages). In another language an iPhone's notices still come out right under a group's name, but a one-to-one chat's (the encryption notice, a changed security code) stay messages from the contact, and a group where only you wrote may not be known for one.
- **A download in several parts** (Meta, Snapchat) must be unzipped into one folder: picked as separate zips, each part is read on its own, so a part with only photos is refused (with that advice) and the chats' photos in it aren't found.
- **Messenger's download of encrypted chats has no chat IDs**: a chat's name stands in, so renaming a group between two downloads makes a second chat; two chats with the same name in one download are kept apart by their files' names, which may not be the same in the next download.
- **A shared export goes into whichever backup runs next**: a one-off backup to another file takes it, and the automatic backup's file then never has it (its copies on the phone are gone). And an updates file carries every export still waiting each time it's written, so a big download is uploaded again with each one until the big file catches up (the catch-up comes sooner, as the updates file counts its size).
- **The phone tells apart exports by their names and a zip's paths** (`Apps.detect`): a WhatsApp chat shared under another name, or Messenger's encrypted-chats download with no JSON shaped like a chat in its first files, isn't recognised when shared (Add a file… in the app's section takes it anyway). Telegram can't export on a phone, so it has no section there.
- **Sharing to the Android app was built and unit-tested, not yet tried on a phone or emulator**: WhatsApp's real "Export chat" share (one .zip, or the .txt and its photos), a big Snapchat download, and a backup run carrying them.
- **The Snapchat for Web reader was checked against the live page, not yet run end to end in the extension**: its reading was run (read-only) in one chat the owner allowed, and the capture, queue and merge are unit-tested, but turning it on in Settings, the background keeping what it sends, and **Put them in my archive** haven't been tried in Chrome yet. Its selectors are generated class names (`ul.MibAa`…), so a Snapchat update can break it: it then reads nothing rather than the wrong thing.
- **Snapchat for Web gives only a group's first time**: a group's later messages are placed just after it, with the span until the next group, so their times in the archive can be minutes early (until the same chat comes in from Snapchat's download, which then matches them). Photos and videos are noted, not saved; message kinds it doesn't know (notices, shared links, Snaps) are left out.
- **Snapchat keeps only saved messages and recent ones**, so its chats come in as partial; snaps (`snap_history.json`: who and when, no content) aren't brought in at all, and its notice types beyond the few known ones (`STATUS…`) come in as "Name: <type in lower case>".
- **Few unit tests.** `npm test` covers only the phone backup import (`test/restore/import-phone.mjs`). The rest of `library.js` is pure and easy to cover the same way (merging, `mediaStatus`, `checkChat`, `summarize`, `parseSums`/`formatSums`, `readLibrary` migrations).
- **The mock test page isn't in the repo.** Recreate it under `test/mock/` from [[Testing]] so anyone can rerun the scenarios. (The big-library generator and the benchmark are: `test/perf/`.)
- **No end-to-end check in CI** beyond syntax and manifest checks.

## Ideas
- Re-check a single chat's photos from the viewer (the master list is already loaded there).
- Show `upgraded_from` and the status in the viewer's lightbox details.
- Let **Check every photo** also offer "Fetch again" for photos whose file changed (today only missing ones).
